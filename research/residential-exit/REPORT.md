## Пауза и одна проверка

Последний известный запрос: **19 сентября 19:06:11 МСК**, API с 10 cookies
нашего профиля → HTTP 403, too-many-requests/CAPTCHA.
При начале этого исследования прошло лишь около 13 минут. Повторять запрос
сейчас и называть это проверкой после длительной паузы было бы неверно.

Предыдущий интервал между известными сессиями был около 4 ч 46 мин:
после 14:11 новых CONNECT в журнале до 18:57 нет, запрос без cookies в 18:57
получил 439. Это не строгий сравнительный тест: endpoint/client/cookies отличались.
403, 429, 439 и текст IP_BLOCKED нужно фиксировать отдельно, не смешивая причины.

Назначен **один** диагностический запуск на **2026-09-20 19:10 МСК**:
`avito-cooldown-once-20260920.timer`, без повторяющегося расписания.

`cooldown_once.py`:

1. Проверяет не менее 24 часов с последней известной попытки в наших артефактах.
   Если появилась более свежая попытка — пропускает запуск, не переносит его автоматически.
2. Берёт общий probe.lock и одноразовый attempt.claim.
3. Измеряет прямой IP через api.ipify.org и отмечает, совпадает ли он с прежним.
4. Запускает временный direct_proxy.py и тот же probe_http.py: одна API-страница,
   те же исходные cookies, кеш API URL; редиректы и повторы отключены. SPFA не вызывается.
5. Останавливает свой транспорт. RuntimeMaxSec=120, Restart=no.

По умолчанию скрипт выполняет только dry-run. Проверены py_compile, сухой запуск,
отказ при недостаточной паузе, отказ при существующем attempt.claim, измерение IP
под теми же capability-настройками systemd. **Результата после 24 часов пока нет.**

Ограничения: не видим обращения других устройств за тем же NAT; если кто-то
пользуется Avito с этого домашнего интернета, полную тишину IP гарантировать нельзя.
Cookies за сутки могут устареть, поэтому новая 403 сама по себе не докажет IP-ban.
При изменении IP тест уже не изолирует эффект одной только паузы. Временный timer
не переживает перезагрузку сервера; тогда проверка не считается выполненной.

Результаты после запуска: `cooldown-result.json`, `probe-output.txt`, `transport.log`
рядом с этим отчётом; HTTP evidence — в `../parser-avito/evidence/<timestamp>/`.

```bash

cat /home/asat/codex-work/avito-monitor/research/residential-exit/cooldown-result.json
cat /home/asat/codex-work/avito-monitor/research/residential-exit/probe-output.txt
```

`sudo systemctl stop avito-cooldown-once-20260920.timer`.

## Отдельный выход через своё устройство

Рекомендуемая схема без изменения default route:

`collector → socks5h://127.0.0.1:18082 → SSH через Tailscale → своё устройство → его ISP`

SSH dynamic forwarding открывает соединение с Avito именно с удалённой машины.
Tailscale нужен только для достижения этой машины за NAT; на сервере не надо
назначать её exit node. Никаких публично открытых SOCKS-портов не требуется.
DNS для целевого сайта передаётся на удалённую сторону через socks5h.

Концептуальная команда, **не выполнялась**, значения нужно заменить:

```bash
ssh -N -D 127.0.0.1:18082 \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  USER@DEVICE_TAILSCALE_IP
```

После установки туннеля сначала проверяется внешний адрес, без обращения к Avito:
`curl --max-time 20 --proxy socks5h://127.0.0.1:18082 https://api.ipify.org`.
Устройство должно иметь SSH-сервер с разрешённым TCP forwarding и отдельный
домашний/мобильный uplink. Для порта SSH, отличного от 22, добавляется `-p PORT`.

| Устройство | Практическая оценка |
|---|---|
| Другой постоянно включённый ПК/мини-ПК на домашнем интернете | Предпочтительно для длительной работы |
| Android на мобильной сети | Реальный кандидат для теста; нужны SSH/SOCKS, питание, проверка сна/фоновой работы |
| Устройство на том же Wi-Fi и WAN | Обычно тот же публичный IP; смены выхода не даст |

В нашем Tailscale на момент проверки виден только Android **S25 Ultra**,
состояние offline, exit_node_option=false. Это не доказывает наличие SSH или
мобильного uplink. Пользователю задан вопрос о доступном другом устройстве.
На телефон ничего не устанавливалось, вход на него не выполнялся.

У upstream ServerProxy жёстко добавляет `http://`; просто вставить socks5h в
AVITO_PROXY текущего runner нельзя. Если туннель будет выбран, понадобится малая
правка proxy adapter или прямое задание socks5h в curl_cffi Session. Сейчас это
только оценка, исходный collector не менялся. Прокси задавать только сессии
collector, без глобальных ALL_PROXY/маршрутов и без fallback на прямой выход.
На новом выходе отдельно проверить сессию/cookies, географию и повторяемость.

Источники: [OpenSSH -D](https://man.openbsd.org/ssh#D),
[libcurl proxy / socks5h](https://curl.se/libcurl/c/CURLOPT_PROXY.html).

Вывод: бесплатный residential-выход уже есть, но он блокировался. Второй свой
домашний или мобильный канал технически можно выделить только collector.
Его доступность и стабильность пока не проверены; ни residential-классификация,
ни SSH-туннель сами по себе не гарантируют отсутствие ограничений Avito.
